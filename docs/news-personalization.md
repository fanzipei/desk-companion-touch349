# 个性化 RSS 新闻

在托盘“设置 → 新闻推荐”启用“个性化 RSS”。可按流程分别选择已有 API、Ollama 或 Unsloth / 本地兼容服务；原 HN / GDELT 流程保留为可选兼容模式。

## 选择新闻模型

“设置 → 新闻推荐 → 流程分工”分别设置新闻推荐、标题翻译、正文简讯和偏好学习的模型。点击“本地处理 + API 推荐”可应用推荐分工，通常让本地模型处理标题翻译和正文简讯，较强 API 负责推荐与偏好学习。截图识别仍使用“模型服务”页的独立配置。旧定时提醒功能已移除，旧数据不再解析、同步或触发。

| 流程 | 推荐配置 | 发送的资料 |
| --- | --- | --- |
| RSS / 网页抓取与正文提取 | PC 直接抓取，不调用大模型 | 请求新闻网站 |
| 新闻推荐 | 现有较强模型 API | 候选标题、来源、时间和偏好档案，不含正文 |
| 标题翻译 | Ollama / Unsloth 本地模型 | 已入选标题；不含偏好档案和正文 |
| 正文简讯 | Ollama / Unsloth 本地模型 | 入选新闻的正文与相关新闻资料 |
| 偏好学习 | 现有较强模型 API | 累计达到门槛的主动反馈、标题和偏好档案，不含正文 |

每项都可独立改为 API、本地模型或“沿用默认新闻模型”。旧配置继续沿用原模型，避免升级时自动发送到未经配置的服务。推荐模型只做筛选和排序，入选后再独立翻译；本地翻译每批最多 6 个标题，使用短序号映射回原新闻 ID，正文简讯串行生成。任一阶段失败保留旧队列，本地服务失败不会自动回退商业 API。

| 来源 | 地址与设置 |
| --- | --- |
| 现有模型 API | 沿用原来的 API 地址、模型名及加密密钥，升级不会自动切换 |
| Ollama | 默认 `http://127.0.0.1:11434`；先在 Ollama 安装模型，再点“读取模型列表”选择；也可手动填写准确模型名 |
| Unsloth / 本地兼容服务 | 填写实际运行的兼容 API 地址，例如 `http://127.0.0.1:8001/v1`；“读取模型列表”通过 `/models` 读取当前提供的模型名 |

在“模型连接与测试”选择要配置的默认服务，读取模型列表、填写模型后点击“测试所选服务”，通过后“保存更改”。使用该服务的流程会共享它的连接配置；显式选择了其他服务的流程不受默认服务切换影响。连接测试只发送合成的 JSON 输出要求，不发送真实新闻、阅读记录或图片。读取模型列表不下载或自动加载新模型。Unsloth 需要先开放推理 API；仅安装训练环境或打开聊天网页不等于已经提供兼容接口。可按 [Unsloth 官方部署说明](https://unsloth.ai/docs/basics/inference-and-deployment/llama-server-and-openai-endpoint)开放服务；导入 Ollama 的 Unsloth 模型则选择 Ollama。

Ollama 使用原生 [`/api/chat`](https://docs.ollama.com/api/chat) 和 [`/api/tags`](https://docs.ollama.com/api/tags)，筛选与偏好学习启用 JSON 输出。长简讯使用普通文本输出。Ollama 上下文默认 16384，可在界面调整；增大上下文会增加内存/显存用量。本地模型等待时间默认 300 秒，可设 30–1800 秒，首次加载较慢时可适当增加。Unsloth 服务的上下文大小由该推理服务设置。

本地正文简讯串行生成，避免多个请求争用显存。较慢的模型可能使一轮处理超过 15 分钟；后台不会并行堆积采集轮次，完成后继续按原时间槽调度。筛选仍先只看标题，只有入选条目才读取正文。小模型筛选使用临时短序号，返回后映射到原新闻 ID，不改变小屏的已读、置顶和删除记录。

本地服务请求绕过新闻/系统代理；本地服务密钥可留空，有需要时单独加密存入 `data/news-local-api-key.dpapi`，不会把原云端密钥发给本地服务。连接失败、输出截断或简讯不合格时保留已有新闻，不自动切换到付费 API。模型或服务切换后区分简讯缓存。HTTP 地址支持 localhost 和局域网 IP；其他远程地址使用 HTTPS。

## 每轮流程

后台运行期间，全部 17 条订阅每 **15 分钟**一起收集，条件请求支持 ETag / Last-Modified。只使用最近 48 小时的条目，每个订阅最多向筛选阶段提供 20 条，跨订阅按规范化网址去重。

1. 收集标题、原文网址、媒体和发布时间，先排除已经删除的条目。
2. 累计满 **20 条主动删除、PC 打开或置顶的有效反馈**时，用已配置的模型更新一次新闻偏好 skill；不足时沿用现有版本。
3. 先按标题排除已发布、广告、过期和近似重复事件，按来源轮换构建候选池；预留探索名额后，推荐模型根据标题和 skill 筛选、排序，翻译模型再处理入选标题。已有兴趣仍侧重国际政治、投资财经和科技，探索部分扩展新话题。
4. **只有入选条目才抓正文、生成 60–120 个汉字的中文简讯**。正文不可读时不依据标题编写长简讯，保留有效缓存并留待后续轮次重试。
5. 同步中文标题、来源和正文简讯到小屏。有效的同篇文章简讯会缓存，模型配置变化后重新生成。

原文仍由触屏“电脑”或全屏长按右滑在 PC 浏览器打开。小屏继续保留自动滚动、双击全屏、进入后 2 秒单击保护、长按左滑删除确认等既有交互。已置顶新闻优先保留，不会被刷新挤掉；已删除网址不会从另一个订阅重新推送。

## 固定探索与新兴趣

新闻队列容量独立于本轮成功生成的数量；本轮少量成功不会替换掉全部旧新闻，详见下文队列规则。

在“设置 → 新闻推荐”可将探索比例设为 **10–60%**，默认 **30%**。例如上限 20 条时，程序尝试预留 6 条探索新闻；有合格的新条目时每轮至少一个探索名额，素材已看过、正文不可读或模型未通过校验时不滥填，也不把旧内容伪装成新探索。

探索名额由程序先分配，模型不能仅凭旧 skill 把它们全部排除。优先最近未推送、展示次数少、近期较少出现的话题，结合有上限的置顶/打开/删除反馈调整；少量删除不会禁止整个主题。话题覆盖国际关系、宏观政策、市场、AI、计算与芯片，以及航天、能源、气候、生命科学、基础科学和产业创新。候选池按来源轮换；同一事件的相似标题会合并，兴趣部分先限制单一话题或媒体占比，来源不足时适当放宽，避免全部条目都来自同一公司或事件。

若模型漏掉程序预留的探索候选，会单独请求它们的标题翻译；此请求不附带已有偏好档案。只有翻译与后续正文简讯均合格的探索条目才发布。探索与兴趣条目穿插显示，小屏标题以“探索”标识。新闻状态会显示实际探索条数、话题数和来源数，方便核对本轮真正发布的结果。

`data/news-exploration.json` 保存最近 2048 条已发布新闻的探索/话题来源、有限的反馈去重记录和话题曝光统计；重复刷新同一新闻不新增一次曝光。反馈仍进入原来的 20 条主动反馈门槛，探索新闻的置顶、PC 打开和确认删除照常学习；事件带上话题及探索来源，帮助偏好模型把“尝试后喜欢的新兴趣”纳入档案。学习提示明确保留证据不足的主题为观察项。

## 新闻队列

默认容量 **30 条**，在“设置 → 新闻推荐 → 新闻队列容量”可设为 **1–50 条**，PC 与小屏使用同一容量。置顶也占用容量，不能把容量设得低于置顶数量。

每轮只把新生成且合格的简讯加入队列前部，保留本轮推荐顺序；原有新闻顺序不因重复筛选或内容更新而提前。队列超过容量时，先淘汰最早入队的**已读且未置顶**新闻；这类新闻不足时，再淘汰最早入队的未读新闻。**置顶固定保留**。缩小容量也遵循此规则，阅读本身不改变列表顺序。

PC 持久保存已读 ID，与小屏离线阅读、PC 打开及微信发送的阅读结果做增量合并，旧状态不会把已读变回未读。微信只在每条新闻的全部分段发送成功后标记已读，不把微信阅读虚构成 PC 打开或置顶偏好反馈。

本轮只成功一条时，只补入一条；全部失败或没有新标题时，旧队列保持不变。已发布的新闻按 ID 和规范化网址去重，已从队列淘汰的文章不会在下一轮重新出现；候选标题缓存不算已发布。删除后留下的空位在之后有新简讯时补足。缩小容量会淘汰多余的非置顶新闻，重新扩大不会复活它们。

PC 概览和推荐状态分别显示“当前队列 / 容量”“本轮新增”“淘汰”数量。小屏新新闻弹窗的累计数统计此前历次到达，手动关闭前可高于队列容量，不能据此判断当前可读条数；已淘汰消息不占当前队列。

首次升级会从历史缓存中恢复最近 48 小时内已经生成且通过校验的正文简讯，补足队列，保留置顶、删除记录和设备已读历史；不会把只抓到标题的候选当作简讯。此恢复只做一次，后续重启不会从历史反复补回旧消息。原默认 20 条升级为 30 条，其他自定义容量保留。`news_deliveries` 在 `data/state.json` 保存最近 4096 条已入队文章的 ID、网址摘要和首次入队时间，用于淘汰后的防重推。

## 小屏未读优先

“下一条”按当前列表顺序寻找未读新闻，必要时从列表末尾绕回开头；只要还有未读，就跳过已经读过的新闻，包括已读置顶条目。“上一条”仍可用于主动回看。

手动翻过、在 PC 打开或置顶新闻时，该条标为已读。进入页面或后台自动刷新本身不算读完。读到最后一条未读后，再切下一条时先显示“未读新闻已读完，即将循环已读新闻”，保留当前画面约 **1.8 秒**，再开始循环已读；本轮循环不会每条都重复提示。有新未读加入后，下一条重新优先未读，新一轮读完时再提示。提示期间新新闻刚提交时也会优先选未读。

操作界面底部显示当前未读数量。已读状态按新闻 ID 独立保存，后台刷新、置顶重排和设备重启都保留；首次更新会从已有设备反馈中接续明确浏览、打开、置顶过的条目。当前最多记忆最近 512 条已读 ID。若刷新保留了当前新闻，则继续显示当前条目和已有阅读位置。

阅读顺序与兴趣学习分开：导航按钮可以把当前条目标为读过，但不会新增兴趣反馈；自动进入已读循环也不会伪造浏览或打开反馈。累计 20 条主动反馈的学习门槛保持不变。

## 新新闻常驻提醒

当当前新闻全部已读，又收到新的未读新闻时，小屏弹出“有新新闻”对话框。提醒一直保留，**手动轻点屏幕后才关闭**；刷新、等待、全屏计时和重启都不会清除待确认提醒。提醒期间暂停自动滚动、自动全屏和翻转切换，并拦住下面的翻页、置顶与删除操作，防止点穿。

对话框显示“累计收到 N 条新新闻”。提醒还未关闭时，后续新推送继续累加；同一新闻按 ID 去重，重复推送、重排或移出后再出现都不会重复计数。即使后台刷新替换了列表，累计数也不回退，因此它可以与当前未读数不同。累计条数和最近 2048 个提醒 ID 一并保存，重启后继续累计。

点击只关闭本轮提醒并把累计计数清零，保留当前阅读位置，不会把新闻标为已读或在 PC 打开原文。之后“下一条”继续优先未读。若列表本来还有未读新闻，新增新闻直接加入列表，不反复弹窗；等这些新闻全部读完后，下一批新新闻才再次触发提醒。首次安装的空列表首次同步不作为“读完后又更新”。

某个源失败时使用尚未过期的缓存；模型输出格式不合格或整轮正文生成失败时保留原有阅读列表。现有 API 模式最多 3 个正文简讯任务并发，本地模式串行。源抓取使用新闻代理设置，现有模型 API 沿用原连接方式，本地推理请求直连所填服务。关闭后台、PC 关机或休眠期间不抓取，恢复运行后继续调度。

## 反馈如何学习

| 明确操作 | 信号 | 权重 |
| --- | --- | --- |
| 置顶新闻 | 最强喜欢，高于 PC 打开 | +8 |
| 在 PC 打开原文 | 强兴趣 | +4 |
| 普通左右滑动切换新闻 | 轻度兴趣，记录刚读完的那一条 | +1 |
| 点“确认删除”删除新闻 | 不感兴趣 | -4 |
| 取消删除、取消置顶、点击导航按钮、自动播放或刷新、切换模式、便签操作 | 中性，不据此推断兴趣 | 0 |

同一轮中对同一条新闻的同类重复操作只作为一份学习证据，避免反复滑动放大偏好。反馈不足时保留初始兴趣，不因单次删除排除整个领域；学习主题兴趣，不推断政治立场、身份、资产和持仓。

学习门槛默认 **20 条**，在托盘“设置 → 新闻 → 偏好学习门槛”可修改。普通滑动只作辅助证据，不计入这 20 条；同一新闻反复打开不能凑满门槛。达到门槛后在下一轮新闻推荐之前学习一次，已处理的反馈不会再次计入门槛，剩余反馈继续累计。新闻收集、标题筛选和正文简讯仍每 15 分钟运行，不受学习门槛影响。

设备保存最近 **64 条尚未确认的反馈**，包含新闻标题、来源域名、动作和序号；重启后仍保留。PC 每约 5 秒补收，先持久化再确认，实时通知与断线补传按“设备 + 序号”去重。离线操作超过 64 条会覆盖最早反馈并记录告警。此新增反馈协议目前用于 3.49 V2 触屏固件。

## 查看与修改偏好 skill

运行数据在仓库的 `data/skills/news-preferences/`，不提交 Git：

- `SKILL.md`：每轮推荐实际读取的偏好。可在“本人明确偏好”段手动补充希望关注或减少的内容；自动学习只更新两个标记之间的学习区。
- `feedback.json`：近期明确反馈、去重序号、已处理进度与学习版本。
- `history/`：每次自动修改前的 skill 文本，便于核对和恢复。

托盘“设置 → 新闻 → 查看 / 编辑偏好 skill”可打开该文件。“立即收集筛选”会立即触发一轮，日常无需操作。资料只发送到对应流程所选的模型；采用上表分工时，商业 API 接收候选标题和偏好反馈，正文简讯在本地处理。便签正文不参与兴趣学习，API 密钥仍使用 Windows DPAPI 加密保存。

“设置 → 新闻推荐”还显示最近成功更新的时间、条数、当前处理阶段或失败原因。模型筛选失败时保留旧新闻，不能把定时任务开始当成成功推送。现有 API 的新闻筛选和偏好学习等待时间为 120 秒，超时、连接故障、HTTP 408/425/429 和 5xx 最多重试一次；HTTP 400 等配置/请求错误不重复请求，保留服务方的简短原因并隐藏密钥。本地推理使用所设等待时间，连接/超时失败留到后续轮次，不立即重复堆积推理请求。原有截图调用仍使用其原等待时间。`data/news-recommendation-status.json` 分别记录尝试时间、处理阶段、最近成功时间和失败原因，成功记录包含新闻模型来源与模型名。

小屏第一行以“【未读】/【已读】”标记当前新闻，操作界面和全屏均显示。沿用已有的阅读判定：切换离开该新闻、PC 打开和置顶会标已读，自动显示、滚动、刷新及关闭新新闻提醒不会。仅标记变化不改变换行和当前滚动位置。

这是持续更新的可读偏好档案，不是微调模型参数。每次学习最多处理 160 条有效主动反馈，并结合少量浏览上下文；不足门槛的剩余反馈继续累计。未处理的主动反馈单独保留，不会被大量普通滑动挤掉；并发到达的反馈不会被错误标为已处理。
